# CLAUDE.md Generator

Scans a project root and produces a `CLAUDE.md` file that gives Claude Code persistent, accurate context on every future session.

## Why this matters

Claude Code reads `CLAUDE.md` at the start of every session. A well-constructed one eliminates the "explain yourself again" tax  Claude already knows the build commands, the stack, the conventions, and the architecture before you type your first message.

---

## Step-by-step workflow

### 1. Determine project root

Default: `$PWD` (current directory in Claude Code).
If the user specifies a path, use that. Confirm before proceeding if ambiguous.

### 2. Run the scanner

```bash
python3 "$(dirname "$0")/../scripts/scan_project.py" [project_root] > /tmp/project_scan.json
```

Read the resulting JSON fully before writing a single line of CLAUDE.md.

### 3. Check for an existing CLAUDE.md

```bash
cat [project_root]/CLAUDE.md 2>/dev/null || echo "(none)"
```

If one exists:
- **Preserve** any sections the user has hand-written (look for comments like `<!-- custom -->` or sections not auto-generable).
- **Merge** the scan data into existing sections rather than overwriting wholesale.
- Tell the user what changed.

### 4. Generate the CLAUDE.md

Use the scan output to fill the template below. **Only include sections for which evidence was found**  never invent commands, never guess. If a field is empty, omit its section rather than writing "N/A".

## Generation rules

**Commands table:** Use only commands from the `commands` field of the scan JSON. Map them to natural-language descriptions using this guide:

| Script name | Description |
|---|---|
| `dev` / `start` | Start development server |
| `build` | Compile/bundle for production |
| `test` / `test:*` | Run test suite |
| `lint` | Run linter |
| `format` | Auto-format code |
| `typecheck` / `tsc` | TypeScript type check |
| `deploy` | Deploy to production |
| `preview` | Preview production build locally |
| `clean` | Remove build artifacts |
| `migrate` | Run database migrations |
| `seed` | Seed the database |
| `generate` | Generate code (Prisma, GraphQL, etc.) |

**Architecture layout:** List dirs found in `architecture.src_structure` and `architecture.notable_dirs`. Annotate each with a role inference:

| Dir name | Likely role |
|---|---|
| `app` / `pages` | Next.js/Remix routing |
| `components` | Reusable UI components |
| `lib` / `utils` | Shared utilities |
| `api` | API routes or NestJS controllers |
| `services` | Business logic layer |
| `hooks` | React custom hooks |
| `store` / `context` | State management |
| `types` | TypeScript type definitions |
| `prisma` / `drizzle` | ORM schema and migrations |
| `infra` / `k8s` / `terraform` | Infrastructure as code |
| `public` / `assets` | Static files |
| `scripts` | Build/automation scripts |

**Env vars table:** List all vars from the scan. For the Purpose column, infer meaning from naming patterns:

- `*_URL` / `*_URI`  Service endpoint
- `*_KEY` / `*_SECRET` / `*_TOKEN`  Authentication credential
- `*_ID`  Resource identifier
- `DATABASE_*` / `DB_*`  Database connection
- `NEXT_PUBLIC_*`  Client-exposed env var (Next.js)
- `VITE_*`  Client-exposed env var (Vite)
- `PORT`  Server port

## Post-generation steps

After writing the file:

1. Print the full contents of `CLAUDE.md` in the chat so the user can review.
2. List any gaps detected  e.g., missing test setup, no .env.example, no description.
3. Offer to fill gaps interactively: "Want me to add a custom Notes section for Claude?"
4. If the project has a `README.md`, offer to sync descriptions bidirectionally.

---

## Edge cases

- **Monorepo**: Generate one root `CLAUDE.md` with workspace map, then offer to generate per-package `CLAUDE.md` files for the heaviest-used packages.
- **Empty/new project**: Generate a skeleton CLAUDE.md with placeholder sections and note: "Project is new  fill commands and architecture as you build."
- **Existing CLAUDE.md**: Diff the new scan against existing content. Only overwrite auto-generated sections. Preserve anything between `<!-- custom -->` markers.
- **No recognizable stack**: List only what was found (config files, notable dirs) and leave stack fields blank with a comment.
- **Private/secret files**: Never read or output `.env` content (only `.env.example`). Never include tokens, passwords, or keys.
